# Отчет по практической работе №2: ER-диаграмма

## 1. Логическая схема базы данных «Автосалон»
Спроектированная ER-диаграмма в нотации Crow's Foot отражает структуру сущностей, типы данных, первичные (PK) и внешние (FK) ключи, а также демонстрационные записи:

![ER-диаграмма Автосалон](diagram.png)

## 2. Типы связей между сущностями
* **BRAND ||——o< CAR** — Одна марка выпускает много моделей автомобилей. Поле `brand_id` является внешним ключом (FK) в таблице `CAR`.
* **CAR ||——o< SALE** — Конкретная модель автомобиля может участвовать в нескольких продажах. Поле `car_id` — внешний ключ (FK) в `SALE`.
* **EMPLOYEE ||——o< SALE** — Один сотрудник (менеджер) оформляет ноль или много продаж. Поле `employee_id` — внешний ключ (FK) в `SALE`.
* **CLIENT ||——o< SALE** — Один клиент может совершить ноль или много покупок в автосалоне. Поле `client_id` — внешний ключ (FK) в `SALE`.

## 3. Подробное описание связи «CLIENT — SALE»
Между сущностями `CLIENT` и `SALE` установлена связь типа `1:N`. 
* **Смысловое чтение:** «Один клиент может совершить ноль или много покупок. Каждая продажа оформляется ровно на одного клиента».
* **Графическое отображение:** На ER-диаграмме связь обозначается как `CLIENT ||--o{ SALE`. Двойная черта указывает на обязательность записи со стороны родительской таблицы, а «воронья лапка» с кружком — на множественность (от 0 до бесконечности) со стороны дочерней.

## 4. Разделение связи M:N (Многие ко многим)
Между сущностями `CAR` и `CLIENT` (какие автомобили покупаются какими клиентами) существует логическая связь «многие ко многим» (`M:N`). В реляционной СУБД её реализация напрямую невозможна. 

Данная связь **уже успешно разбита** на две независимые связи `1:N` через промежуточную (связующую) сущность **`SALE`**:
* `CAR ||--o{ SALE`
* `CLIENT ||--o{ SALE`

Сущность `SALE` аккумулирует в себе внешние ключи обеих таблиц, дополняя связь важными транзакционными атрибутами (`sale_date`, `amount`).

## 5. Ограничения на NULL / NOT NULL для атрибутов
Ниже представлена сводная спецификация полей, определяющая обязательность заполнения данных в системе:

| Сущность | Атрибут | NULL? | Описание |
| :--- | :--- | :--- | :--- |
| **BRAND** | `brand_id` | NOT NULL (PK) | Первичный ключ |
| **BRAND** | `brand_name` | NOT NULL | Наименование марки автомобиля |
| **BRAND** | `country` | NULL | Страна происхождения (необязательно) |
| **CAR** | `car_id` | NOT NULL (PK) | Первичный ключ автомобиля |
| **CAR** | `model` | NOT NULL | Название модели |
| **CAR** | `year` | NOT NULL | Год выпуска |
| **CAR** | `price` | NOT NULL | Стоимость |
| **CAR** | `brand_id` | NOT NULL (FK) | Ссылка на марку автомобиля |
| **CLIENT** | `client_id` | NOT NULL (PK) | Первичный ключ клиента |
| **CLIENT** | `full_name` | NOT NULL | ФИО клиента |
| **CLIENT** | `phone` | NULL | Контактный телефон (необязательно) |
| **CLIENT** | `email` | NULL | Электронная почта (необязательно) |
| **EMPLOYEE** | `employee_id` | NOT NULL (PK) | Первичный ключ сотрудника |
| **EMPLOYEE** | `full_name` | NOT NULL | ФИО сотрудника |
| **EMPLOYEE** | `position` | NOT NULL | Должность менеджера |
| **EMPLOYEE** | `phone` | NULL | Контактный телефон сотрудника |
| **SALE** | `sale_id` | NOT NULL (PK) | Первичный ключ продажи |
| **SALE** | `sale_date` | NOT NULL | Дата совершения сделки |
| **SALE** | `amount` | NOT NULL | Финальная сумма сделки |
| **SALE** | `car_id` | NOT NULL (FK) | Ссылка на проданный автомобиль |
| **SALE** | `client_id` | NOT NULL (FK) | Ссылка на покупателя |
| **SALE** | `employee_id` | NOT NULL (FK) | Ссылка на оформившего сотрудника |
